# Offline time-of-use settlement

`obsdeps billing` turns cumulative meter readings and local tariff rules into
reviewable bills. It reads only local files (or an immutable local SQLite
database), never touches the network, and never asks a human to fix a reading
by hand. Every number it emits carries the evidence needed to recompute it.

Pure Python 3.9+, standard library only (`zoneinfo`, `sqlite3`, `decimal`,
`fractions`).

---

## 1. Inputs

Four JSON documents, each an array.

### Meters

```json
[
  {"meter_id": "M1", "timezone": "America/New_York"},
  {"meter_id": "M2", "timezone": "Europe/Berlin", "modulus": 100000}
]
```

* `timezone` is an **IANA** name. Every timestamp for the meter must carry the
  offset that this timezone actually has at that instant (see §4).
* `modulus` is optional. When present it is the exclusive upper bound of a
  rolling counter, and readings must lie in `[0, modulus)`. See §5.

### Readings

```json
[
  {"meter_id": "M1", "timestamp": "2024-03-14T00:00:00-04:00", "watt_hours": 0},
  {"meter_id": "M1", "timestamp": "2024-03-14T12:00:00-04:00", "watt_hours": 6000}
]
```

* `timestamp` is **RFC 3339 with a mandatory UTC offset** (`Z` or `±hh:mm`).
* `watt_hours` is a finite, non-negative cumulative counter value.

### Tariffs

```json
[
  {
    "tariff_id": "TOU",
    "rate_unit": "per_kwh",
    "weekday_rules": [
      {"weekdays": [1, 2, 3, 4, 5], "rules": [
        {"label": "OFF",  "start": "00:00", "end": "07:00", "rate": "0.10"},
        {"label": "PEAK", "start": "07:00", "end": "24:00", "rate": "0.20"}
      ]},
      {"weekdays": [6, 7], "rules": [
        {"label": "WEEKEND", "start": "00:00", "end": "24:00", "rate": "0.06"}
      ]}
    ],
    "day_exceptions": [
      {"date": "2024-03-15", "label": "HOLIDAY", "rate": "0.05"}
    ]
  }
]
```

* `weekdays` use ISO numbering: 1 = Monday … 7 = Sunday. Every weekday 1..7
  must be covered.
* Each rule is a **half-open** local interval `[start, end)`. `end` may be
  `24:00`. The intervals on one weekday must tile the full day with no gap and
  no overlap (two rules may share a *label*, e.g. one night rate on both sides
  of midnight; only time intervals must not overlap).
* `rate_unit` is `per_kwh` (default) or `per_wh`. Rates are non-negative.
* `day_exceptions` name a local calendar date (`YYYY-MM-DD`) with a single
  all-day label and rate. An exception **always beats** the weekday rule on
  that date.

### Periods

```json
[
  {"period_id": "P1", "meter_id": "M1", "tariff_id": "TOU",
   "start": "2024-03-14T06:00:00-04:00",
   "end":   "2024-03-15T00:00:00-04:00",
   "currency": "USD"}
]
```

The period is the half-open real-time interval `[start, end)`. Both
boundaries are RFC 3339 timestamps whose offsets must match the meter
timezone. `currency` defaults to `USD`.

## 2. Running it

### CLI

```bash
# Direct file mode: reads four files, writes nothing, prints the bill document.
python3 tools/obsdeps_cli.py billing settle \
    --meters meters.json --readings readings.json \
    --tariffs tariffs.json --periods periods.json > bill.json

# Or register the inputs immutably in SQLite, then settle from the database.
python3 tools/obsdeps_cli.py billing register --db billing.sqlite3 \
    --meters meters.json --readings readings.json \
    --tariffs tariffs.json --periods periods.json
python3 tools/obsdeps_cli.py billing registered --db billing.sqlite3
```

Exit codes: `0` every period settled; `2` at least one period rejected (valid
bills are still printed); `1` usage error or an unparseable input file.

### Python API

```python
from obsdeps.billing import BillingApi

# File mode (no database, inputs never modified).
with BillingApi() as api:
    result = api.settle_files(
        meters="meters.json", readings="readings.json",
        tariffs="tariffs.json", periods="periods.json")

# In-memory documents.
with BillingApi() as api:
    result = api.settle_documents(
        meters=meters, readings=readings,
        tariffs=tariffs, periods=periods)

# Registered, immutable SQLite mode.
with BillingApi("billing.sqlite3") as api:
    api.register_inputs(meters="meters.json", readings="readings.json",
                        tariffs="tariffs.json", periods="periods.json")
    result = api.settle_registered()
```

The result always has two buckets: `bills` (settled periods) and `rejected`
(periods with structured `problems`), plus a `summary`. Independent meters and
periods never block each other.

### Worked, hand-checked example

```bash
python3 examples/run_billing_example.py
```

Its expectations are computed on paper and embedded in the script, not
generated by the engine.

## 3. The calculation

For each meter/period:

1. **Find covering readings.** The last reading at or before `start` and the
   first at or after `end`; readings exactly on a boundary count. If either is
   missing, the period is rejected (`missing-boundary-reading`).
2. **Assume constant consumption between adjacent readings.** A clip of `c`
   real seconds inside a reading pair lasting `d` seconds owns `c/d` of the
   pair's energy. All intermediate arithmetic is exact `fractions.Fraction`.
3. **Split real time at tariff boundaries.** Every rule start/end wall time is
   mapped to the real UTC instant(s) on which that wall clock actually
   occurs, and each clipped interval is cut there. Energy is then summed per
   `(label, rate)` detail.
4. **Reconcile and round.** Detail usages are made to sum *exactly* to the
   boundary-derived total (largest-remainder allocation at 9 decimal places).
   Money per detail is rounded **half-up to the cent after aggregation**.

A settled bill contains, per detail: `watt_hours`, declared `rate` and
`rate_per_wh`, exact `amount_precise`, rounded `amount`, and the
`rule_sources` (weekday rule locator or the specific day exception). It also
lists every `segment` with its reading pair, clip interval, `pair_seconds`,
`allocated_seconds`, per-slice seconds and local/UTC times, the participating
and boundary readings, and the interpolated boundary counter values.

---

## 4. Time interpretation and daylight saving

* All internal computation uses **real UTC instants and real elapsed
  seconds**. A local clock label is never treated as a duration.
* Every input offset is checked against the meter's IANA timezone **at that
  instant**. A reading or period boundary whose offset disagrees is rejected
  with `offset-mismatch`; the bill is never produced from a guessed offset.
* **Fall-back (repeated local hour).** The repeated wall time maps to two
  distinct real UTC ranges. They are priced as two segments, each with the
  rate in force on its real timeline, and the second carries PEP 495
  `fold=1` in the evidence.
* **Spring-forward (missing local hour).** No real instant carries a wall
  time inside the gap, so no slice and no energy is ever created for it. A
  rule boundary whose wall time falls inside the gap becomes effective at the
  post-gap instant; the gap's real seconds keep the last pre-gap rule. The
  bill's total seconds reflect the shorter real day.

---

## 5. Counter roll-over (modulus)

Readings sorted by real time must be non-decreasing. A decrease is accepted
**only** when:

* the meter explicitly configures a `modulus`, and
* both the earlier and the later value are in `[0, modulus)`.

It is then counted as exactly one wrap, adding the modulus once to the
difference (`energy = later - earlier + modulus`). Anything else — a decrease
with no modulus, or a value outside the valid range — rejects the period with
`reading-rollback`, naming both readings.

Duplicate readings at the same real instant with the same value are merged.
Different values at the same instant reject the period with
`duplicate-reading-conflict` and report both values; the engine never picks
one silently.

---

## 6. Precision and rounding

* Energy is carried as exact `fractions.Fraction`; conversions to `Decimal`
  use 50 significant digits.
* Detail usages are displayed at 9 decimal places and adjusted by
  largest-remainder so they sum **exactly** to the usage derived from the
  boundary readings (also interpolated exactly).
* `amount_precise` keeps the unrounded money; `amount` is that value rounded
  `ROUND_HALF_UP` to two decimal places. The bill total is the sum of the
  rounded detail amounts, so the printed lines always add up.
* Repeated runs over identical inputs produce byte-identical output, and
  input files are never modified (verified by digest in the test suite).

## 7. Rejection codes

| Code | Cause |
| --- | --- |
| `meter-unknown` / `tariff-unknown` | referenced entity missing or itself invalid |
| `meter-malformed` / `meter-duplicate` | meter entry is not an object or the id repeats |
| `meter-timezone-missing` / `meter-timezone-unknown` | missing or unrecognised IANA timezone |
| `meter-modulus-invalid` | modulus missing/invalid (must be a positive finite number) |
| `reading-timestamp-malformed` / `reading-value-malformed` | unparseable reading field |
| `offset-mismatch` | input offset differs from the timezone offset at that instant |
| `missing-boundary-reading` | no reading on/before `start` or on/after `end` |
| `duplicate-reading-conflict` | two values at one real instant disagree |
| `reading-rollback` | counter decreased without a legal modulus wrap |
| `tariff-malformed` / `tariff-duplicate` | tariff entry is not an object or the id repeats |
| `tariff-rules-missing` / `tariff-rate-unit-invalid` | no weekday rules or an unknown `rate_unit` |
| `tariff-rule-malformed` | bad rule label or half-open interval |
| `tariff-gap` / `tariff-overlap` | weekday rules do not tile the day |
| `tariff-day-uncovered` | a weekday has no rules |
| `tariff-rate-invalid` | rate is missing, negative or non-numeric |
| `tariff-exception-malformed` / `tariff-exception-duplicate` | bad or repeated day exception |
| `period-boundary-malformed` / `period-empty` | unparseable boundary or `start >= end` |
| `period-duplicate` / `period-currency-invalid` | repeated period id or empty currency |

A rejected period never yields a partial bill, and never prevents an
independent meter/period from settling.
